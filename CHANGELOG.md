# Changelog

Bump `VERSION` and add an entry for every change that projects will pick up on upgrade. Call out anything that changes agent behavior (core rules, built-in skills), since those land in every project at once.

## 0.3.0-dev (unreleased)
- **New: the debug workflow pack** (`install.sh --workflow debug`, roadmap row 48). A debugging skeleton the agent follows with the repo's own tools: `kinds/bug.md` for bug reports, a project-owned playbook (`.agents/debug/playbook.md`, drafted by harness-tailor) that binds each step to skills, commands, and docs, and the `debug` command (`.agents/commands/debug`): `start`, `run` (every command captured as evidence, after a policy check), `outcome`, `status`, `close` (`abandoned`, `duplicate`, or `reviewed` when `DEBUG_ASK` is empty), and `approve` / `reject`, which only a person runs. An approval binds the hash of `root-cause.md`; approvals and closes are recorded in `.git/ai-harness/debug-approvals` and count only for the session they were made for. Checks: a reproduction attempt with its outcome before the check-in (`debug-no-repro-attempt`), `root-cause.md`'s fixed headings and a confidence the attempts support (`debug-format`), cited evidence `debug run` captured and hypotheses that exist (`debug-evidence-missing`), no experiments left once the root cause is written (`debug-experiments-left`), no commits to project code during a session (`debug-committed`), the playbook's format (`debug-playbook-format`), and approvals only `debug` recorded (`debug-approval-unrecorded`, `debug-approval-simulated`, `debug-simulated-human`, policy blocks). It investigates and stops at a root cause you approve; the fix goes through the project's own process. Its policy rules, appended to `.agents/policy.conf` once, keep agents from running `debug approve` and `reject`. Sessions stay local (`.agents/debug/sessions/`, gitignored by the seeded `.gitignore`). `DEBUG_*` settings come from `.agents/harness.conf` only, never the environment. See `workflows/debug/README.md`.

- **Fix: agents can't switch the commit hooks off the plain ways** (roadmap row 36, pilot 2 issue 11). `--no-verify` and `git commit -n` were blocked, but `git -c core.hooksPath=/dev/null commit`, `git config core.hooksPath /dev/null`, and `rm .git/hooks/commit-msg` weren't, and all three skipped the commit-msg checks. gitflow's agent check now refuses setting `core.hooksPath`: `git -c` and `--config-env` for one command, and `git config` in any scope or file, including `--unset`, `--add`, `--replace-all`, `git config set`/`unset`, and removing or renaming the `core` section. Reading it (`git config core.hooksPath`, `--get`) is fine, and gitflow's `install-hooks` still leaves an existing `core.hooksPath` alone. Known gaps lists the spellings it doesn't catch. Also fixed in gitflow's agent check: a git option it didn't know before the subcommand (`git -p push`, `git --git-dir .git commit -n`) ended the check with nothing checked, and a `-C` or `-c` with nothing after it looped until the hook's timeout. **Behavior change:** agents get a deny for those commands; a person can still run them. **Upgrading:** re-run `install.sh`; the `core.hooksPath` check is in gitflow, which is harness-owned, so it arrives on its own. policy.conf is project-owned, so existing installs add the `.git/hooks/` rule themselves: copy the `deny-regex` line that mentions `.git/hooks` from the template's `.agents/policy.conf` (right after `deny-arg --no-verify`) into yours.
- **Fix: a tier step's exit 2 is a failure, not a policy block** (roadmap row 45). `agents_step` returned the command's exit code as it was, so `make`, a test binary, or a linter that exits 2 on failure made `verify` say `BLOCK` (a policy block) instead of `FAIL`. It now returns 1 for 2; its `FAIL <step> (exit 2)` line still shows the real code, and 0, 1, 3, and 124 come back unchanged. No stack or workflow pack routes a real policy block through `agents_step` (feature-driven's forged-approval check exits 2 on its own). The python stack's `py_run` keeps its own 2-to-1 mapping, since a tier script can call it without `agents_step`. **Behavior change:** a test binary run from a cpp-cmake tier script (`agents_step tests "$AGENTS_ROOT/$CPP_BUILD_DIR/<binary>"`) that exits 2 now reads `FAIL verify turn`, not `BLOCK`; the stop gate blocks on both, so the change shows in the label and in verify's exit code (1, not 2). **Upgrading:** re-run `install.sh` (feedback.sh is harness-owned).
- **New: the hooks log tool names they don't know** (roadmap row 6). The pre-tool and post-edit hooks write a tool name that isn't one of their shell, read, edit, or question tools to `.agents/cache/hook-events.log` as a tab-separated `<time> <tool> <event> unknown-tool <name>` line, once per session and event (a payload with no session id counts as one long session; deleting the log starts over), so an edit or shell tool the hooks miss (VS Code's, through Copilot's hooks, which see every tool call) shows up during the live checks. Only the name is logged, never the tool's input, with anything outside letters, digits, and `_.:@/+-` replaced by `?` and a cap of 64 characters; a payload with no name logs `(none)`. MCP tools and Copilot CLI's `web_fetch`, `web_search`, `update_todo`, and `task` aren't unknown. Nothing is logged while that hook's feature is off in `HOOKS` (`policy` for pre-tool, `edit` for post-edit) or with `AGENTS_HOOKS=off`, and the hook's answer and output don't change. List them with `grep unknown-tool .agents/cache/hook-events.log | cut -f2,3,5 | sort -u`. **Behavior change:** none for agents; the log gains a few lines, and the cache a small `tools-<session>` file per session that saw one. **Upgrading:** re-run `install.sh` (the hook is harness-owned).

- **Fix: `--help` never runs a step.** `gitflow start --help` used to create a branch named `help`, `gitflow commit --help` committed whatever was staged with `--help` as the message, and `gitflow push --help` pushed. Every gitflow step (`config`, `status`, `start`, `commit`, `template`, `update`, `check`, `push`, `pr`, `review`, `merge`, `install-hooks`) now prints its own usage on `gitflow <step> --help` (or `-h`), changes nothing, and exits 0. `tasks` does the same for every command (before, `tasks add <slug> --help` added a task called `--help`, and `ask`, `answer`, `log`, `link`, and `record` recorded it too). `guard allow`, `eval`, `sync`, `policy test`, and the feature-driven pack's `fdd` print their usage on `--help` too (anywhere in their arguments, since their help path writes nothing).
- **Behavior change: unknown options are refused.** An option gitflow or tasks doesn't know (`gitflow push --force`, `gitflow commit -m x`, `tasks link <slug> --force`), an argument a gitflow step doesn't take (`gitflow status extra`, `gitflow push origin`), or `-h`/`--help` among other words (`gitflow commit fix -h parsing`, where exit 0 would read as a commit that happened), is now refused with the step's usage and exit 3 (the usage-error code `verify` and `policy` already use), before anything changes. Before, it became part of the branch name, commit subject, or recorded text, or was ignored. A summary or text that starts with `-` goes after `--` (`gitflow commit Handle -- -v`, `tasks log <slug> -- -x was odd`); `tasks ask` and `tasks questions` now take `--` too. `gitflow pr` with an unknown option exits 3 instead of 1. `gitflow start` now takes `--type=` after the summary as well, as its usage always said. The policy hook lets an agent run exactly `gitflow <step> --help` for a step outside `GIT_AGENT_MAY`; native deny rules, where rendered, still block it.

The stop gate lets exit 3 through as before, so agents aren't blocked; `verify --tier=full` in CI fails until it's settled. A new setting, `CPP_NO_TESTS=ok`, turns the report off. When `cpp_test_affected` picks tests by a regex that matches nothing CTest lists, it now runs them all instead.

The pack then judges the turn's own commits, on whichever branch and whether made with `git commit`, `gitflow commit`, skipped git hooks, or an amend, plus what's uncommitted. - **New (feature-driven): `install.sh --simulated-human`, for flows where an agent plays the person** (roadmap row 40). Scratch runs, pilots, and demos had an orchestrating agent approve FDD gates with `env -u CLAUDECODE`, the same bypass Known gaps lists. The new flag turns on a per-clone switch in the git dir (`.git/ai-harness/simulated-human`, holding a hash of a token and how it was turned on, plus a matching line in the approval record) and prints the token once. A shell with `AGENTS_SIMULATED_HUMAN=<token>` may then run `fdd approve`, and install's adoption, even if an agent tool started it; agents working in the clone don't have the token, so they're refused as before. Every approval made or adopted while the switch is on is marked simulated (`approved design F-1 (simulated human)`, a who field ending in `(simulated human)` in `approvals`, `#simulated` lines in the record for adopted ones) and counts only while it's on; with the switch gone, they're `fdd-approval-simulated`, a policy block. `fdd status` starts with `simulated human: on (...)`, `verify` prints a note, and each `install.sh` run says so. A switch not written by `install.sh --simulated-human` is off and is `fdd-simulated-human` (exit 2); the hooks flag one that appears or changes during an agent turn (the pre-tool hook, before the next tool call, and the stop gate) or whose token is in an agent session's environment (session and turn start), and a flagged or read-only switch stays off until `install.sh --simulated-human` runs again (it writes a new token). If the switch can't be turned on (the pack in use predates it, or writing it failed), install.sh finishes and then exits 3. The flag needs a git repo, python3, and an active workflow pack with human gates (feature-driven, debug) in `WORKFLOWS`, and is refused (exit 2) before anything changes otherwise. A token you set in `AGENTS_SIMULATED_HUMAN` before the run is used instead of a generated one; it needs 16 characters or more.

- **Fix (feature-driven): no new work on an inspected feature** (pilot 2, issue 9). Hand-made packs in `.agents/workflows/<name>` move to `.agents/library/workflows/<name>`, mentions of the old path in their files updated and, for an active pack, its skill folded in as `skill/`. Stacks become shims (a hand-made one moves to `.agents/library/stacks/` first). If both the old and new path exist, install warns and leaves both. The feature-driven `deny-cmd` rule in policy.conf is pointed at the new `fdd` path. Team mode prints the moves; commit what `git status` shows (the new `.agents/builtin/` and `.agents/library/`, renames, removals, and skills that became links). Local mode does it quietly. `skills.lock` needs no change: pins are by name and the content is the same. **Pack authors:** scripts must find their own files from their own path, not `.agents/workflows/<name>/` (README, Libraries). New `LIBRARIES` setting: existing harness.conf files don't have the line, which means none. Switching an old-layout team install to local (`install.sh --local`) migrates it the same way, so old copies of built-in skills don't end up in `.agents/library/`. An unedited old copy of a pack with `seed/` files (feature-driven) is removed like any other, not kept as differing. Re-running install with an old-layout hand-made pack's `--workflow`/`--stack` flag works.
- **Local mode backup.** `sync` keeps a copy of the local harness files (minus the cache, eval results, and `.agents/builtin/`, which `install.sh` rebuilds) in the worktree's git dir (`$(git rev-parse --git-path ai-harness)/backup`, or `backup-<prefix>` for a subdirectory install), where git clean, stashes, and checkouts don't reach. It's refreshed on every `sync` and whenever `verify` runs on the turn or full tier; edits since then aren't in it. If `.agents/` goes missing, `install.sh` restores it from there instead of seeding blank files. A local `AGENTS.md` replaced by a newly tracked one is kept as `AGENTS.md.before-tracked`, and the next `sync` says so once. Team mode keeps no backup; switching to it deletes one, except a saved `AGENTS.md.before-tracked`.
- **Policy:** agents can't run `git clean` with `-x`/`-X` or `git stash -a`/`--all` (or `--a`/`--al`), including after git options like `-C dir` or `-c key=value`; both take a local install away. `git stash -u` stays allowed. After a `git stash -a`, pop the stash rather than re-running `install.sh`. **Upgrading:** policy.conf is project-owned, so existing installs add the two `deny-regex` lines from the template's policy.conf themselves.
- **Local install mode.** `install.sh` installs local by default: everything it adds stays out of git in your clone (an exclude block in `.git/info/exclude`, `.claude/settings.local.json`, and `.agents/AGENTS.local.md` / `CLAUDE.local.md` when the project already tracks `AGENTS.md` / `CLAUDE.md`), and files the project tracks are never modified. `install.sh --team` commits the harness for the whole team and CI, as before. `verify` adds a `harness-tracked` finding if any of it gets committed by accident. **Behavior change:** new installs are local by default; pass `--team` for the previous, committed setup.
- **Upgrading:** existing installs keep today's behavior unchanged (a missing `HARNESS_MODE` means `team`). Run `install.sh --local` to switch one to local mode: it untracks the harness's own files and removes its entries from shared files it touched, stripping them in place or untracking a file that held nothing else, then tells you what to commit. Stripping a JSON or TOML config needs python3; without it, the switch stops before changing anything when one of them holds harness entries (see the install --local fix above). `install.sh --team` switches back. Local-mode files are git-ignored, so `git clean -fdX` deletes them, tailoring included; re-run `install.sh` to restore them from the backup (see Local mode backup).
- **Fix (sync):** regenerating the `CLAUDE.md` stub keeps `@` imports someone added to it (before, they were replaced with `@AGENTS.md`). A `.claude/settings.local.json` (team mode) or untracked `.claude/settings.json` (local mode) with no harness entries is left alone; before, an empty `{}` one was deleted. Team mode no longer rewrites `.git/info/exclude` when it holds no harness block and you have no personal skills to keep out of git (see Personal skills). Picked up on upgrade.
- **Workflow packs.** `install.sh --workflow <name>` installs a process skill plus checks that `verify` runs after the project's tier scripts for every pack in `WORKFLOWS`. First pack: `req-driven` (generic requirements traceability: unknown IDs, untagged new tests, untraced changes, trace report, optional untested-requirement gate).
- **Pack extension points.** A workflow pack can ship a `policy.conf.snippet` (appended once, keyed on its first-line marker comment, so deleted rules stay deleted), `seed/` files (created once, never overwritten), and `checks/commit-msg.sh` (run by gitflow wherever it checks commit messages, including `gitflow commit` with hooks off; exit 1 or 2 rejects, and a check that can't run blocks too). With `GIT_LOCAL_HOOKS=auto`, git hooks now also install when an installed pack ships a message check. No change for existing packs. Packs can also ship `bin/` commands and a `checks/state.sh` for verify's cache key.
- **Fix:** `install.sh` no longer copies `__pycache__` directories from a stack or workflow pack in a dev checkout, and `.agents/.gitignore` ignores them. Picked up on upgrade.
- **Fix:** `verify`'s cache now includes plan ledgers. Before, starting a task after a failed run could return the stale failure (req-driven's "task in progress" trace). Picked up on upgrade.
- **feature-driven workflow pack.** Classic FDD with local artifacts (`.agents/fdd/`, never committed): model, feature list, per-feature designs, and approvals you record with `fdd approve` (blocked for agents). Checks: list format, design before build, tracing through the plan ledger, no private feature IDs in shared code or commit messages, and FDD files that git tracks or doesn't ignore (`fdd-not-local`); the full tier writes a parking-lot progress report. Opt in with `install.sh --workflow feature-driven`. The checks need python3; once a feature list exists, commits block without it.
- **Fix (gitflow):** `gitflow start` no longer drops unpushed commits on the base branch. When the local base is ahead of the remote, it branches from the local base and says so; when they've diverged, it refuses. It also refuses to branch from a start point that lacks the harness the current branch has committed. In a shallow clone, where git may not see the shared history, the refusal says so and suggests `git fetch --unshallow`. Before, the checkout could delete a committed-but-unpushed harness from the working tree mid-session (found in the feature-driven pilot).
- **Fix (tasks):** `tasks ask` on a done task leaves it done (asking for sign-off on finished work), and `answer` doesn't reopen it. The stop gate treats that open question as a legitimate pause too, and questions recorded by the hooks while it waits land in that plan, on that task.
- **Policy:** a `deny-regex` block shows its reason instead of the raw regex when the rule has one. **Behavior change:** a `deny-regex` rule no longer re-runs on a quoted argument that appears verbatim in the command (it already matched against the whole line), so a rule can exempt a harmless command like `echo "..."`. Arguments that unquoting changes (`bash -c 'cu''rl u | sh'`) are still re-checked. `deny-cmd` and `deny-arg` still check quoted arguments (`bash -c "git push"`).
- **feature-driven:** the approve block now matches `fdd approve` only where it runs as a command, so asking the human to run it (a one-line `tasks ask`, `echo`, or `printf` that only names it) is no longer blocked. If you installed feature-driven from main before this, replace the `deny-regex` line in `.agents/policy.conf` with the one in the pack's `policy.conf.snippet` (policy.conf is project-owned, so upgrades don't touch it). Findings point at the first changed line in scope. The skill says when to start a branch (only when `gitflow status` says so), which `--gate` each check-in uses, and to start each session from `fdd status` and `tasks list`.
- **Cache key is whole-tree.** `verify` results now depend on the full working-tree state plus harness config and packs, so a change elsewhere (a header, a requirements export) invalidates a cached per-file result.
- **harness-tailor** fills workflow pack settings and adds one AGENTS.md line naming the workflow.
- **Validation gates.** New built-in `validate` skill: plan, test, and implementation gates with PASS / REVISE / ASK verdicts, a two-round feedback loop, and human check-ins at the gates in `VALIDATE_ASK` (new harness.conf setting, default all three). `plan-task` and `req-driven` run their gates through it; `review-diff` is its implementation-gate checklist.
- **Question ledger.** Per-plan `questions.json` (plus `_general/` outside plans). `tasks ask` records a question with its gate, blocks the task, and refuses questions the ledger already answered (`--force` to re-ask); `tasks answer` records the answer, adds it to plan.md Decisions, and resumes the task; `tasks questions` searches all questions and answers. The stop gate pauses while a task waits on an answer, so a test gate can stop on deliberately failing tests.
- **`questions` hook feature** (on by default in new installs; add it to `HOOKS` in existing ones): before a question-tool call, an earlier answer is shown instead (once per session); after it, question and answer are recorded; a new session starts with a reminder of open questions. Claude Code and Copilot; Cursor has no question tool to hook.
- **Core rules** mention that plan-task's gates use `validate` (one line).
- **Git workflow.** New `.agents/bin/gitflow` (start, commit, update, check, push, pr, review, merge, install-hooks) driven by `.agents/git.conf` over a personal `~/.config/ai-harness/git.conf`. Templates for branch names and commit subjects both generate and validate; trailers, protected branches, PR base and tool (gh, glab, none), merge method, and `GIT_AGENT_MAY` (which steps agents may take). Enforced by local `commit-msg` and `pre-push` hooks, the policy hook, and, when the project sets `GIT_AGENT_MAY`, native deny rules. New `git-workflow` skill; harness-tailor proposes git.conf from repo history.
- **Generic by default.** Nothing is protected unless configured (`GIT_PROTECTED` takes any names or globs, e.g. `dev/main release/*`, and `{base}` for the base branch). Local git hooks install only when git.conf has something to enforce (`GIT_LOCAL_HOOKS=auto`), and `sync` adds them once it does. A verify tier that can't run is reported by `gitflow check`, not treated as a failure. Placeholders with no data (no ticket, no linked plan) leave no gaps in the PR body. `tasks link` optionally ties a plan to its branch for `gitflow pr`. "Absence" tests cover a zero-config trunk repo, gitflow with no plan or ticket, a plan with no workflow, and a workflow with no git config.
- **Commit templates.** `GIT_COMMIT_TEMPLATE` (or the repo's local `commit.template`) defines the whole message: subject, sections (required unless the guidance line says `(optional)`), and trailers, with self-filling placeholders. A `prepare-commit-msg` hook prefills the editor for humans; `gitflow commit --section Label=text` fills it for agents; `gitflow template` describes it; the `commit-msg` hook validates every message (including section values like `Refs: {ticket}` against the branch's ticket) and drops optional sections left empty. With no template, nothing changes.
- **Development setup.** New `tests/lint.sh` (fast static gate, including checks that new CLIs and skills are wired into `install.sh` and that the harness never gets installed into its own repo), `tests/all.sh` (smoke under every awk), `scripts/package.sh` (release zip plus SHA-256) and CI on Ubuntu and macOS bash 3.2. None of this ships in the release zip.
- **Fix (cpp-cmake):** the sanitizer tier no longer sets `detect_leaks=1`. Apple clang's ASan aborts every test at startup when it's set, so on macOS the full tier failed every test. Linux keeps leak checks, since ASan enables them by default there. Your own `ASAN_OPTIONS` still wins. Picked up on upgrade.
- **Behavior change:** the core rule "no git push, commit only when asked" becomes "follow this repo's git workflow; steps outside `GIT_AGENT_MAY` are the human's". The default `GIT_AGENT_MAY` is `branch commit`, so agents still don't push by default.
- **Upgrading:** new installs drop `deny-cmd git push` and `deny-cmd git rebase` from policy.conf because git.conf covers them. Existing policy.conf files are project-owned and keep those lines, which still win; remove them to let git.conf decide. Add `questions` to `HOOKS` in harness.conf to get the question hooks.

## 0.2.0
Changes agent behavior in every project: the core rules are rewritten and hooks are on by default.

- **Core rules trimmed** to ~20 lines of non-inferable directives. No version string in the managed block, so it stays cache-stable across upgrades.
- **Feedback layer.** `verify` is now a harness-owned orchestrator with edit, turn, and full tiers that run project-owned `.agents/checks/{edit,turn,full}.sh`. New `check` (edit tier) and `guard` (suppressions, skipped or deleted tests). Shaped output, logs on disk, budgets, caching by tree state, baselines, `--json`.
- **Hooks** for Claude Code, Copilot (CLI, cloud agent, VS Code), and Cursor: policy enforcement before tool calls, `check` after edits, and a bounded stop gate that runs `verify` on turns that changed files. `AGENTS_HOOKS=off` disables them.
- **Policy** in `.agents/policy.conf`, enforced by the hook and rendered into Claude deny rules and Codex execpolicy rules.
- **Adapter rendering** merges into existing `.claude/settings.json`, `.cursor/hooks.json`, and `.gemini/settings.json` without touching other entries. Default `ADAPTERS` is now `claude copilot cursor`.
- **Plan ledgers.** `plan-task` now uses `.agents/plans/<slug>/{plan.md,tasks.json,progress.log}` through the new `tasks` CLI. Old single-file plans aren't migrated.
- **Integrity.** `sync --check` also fails on changed pinned skills (`sync --lock-skill`) and invisible Unicode in instruction files.
- **Evals.** `eval new/run/report` replays real fixes across arms A (no harness), B (hooks off), C (full).
- **Stack packs.** `install.sh --stack <name>`; first pack: `cpp-cmake`.
- **Skills.** `harness-tailor` proposes facts-only tailoring under a line budget and fills the tier scripts; `plan-task` covers the ledger and session hygiene; `review-diff` focuses on what tools can't see.
- **Requires python3** for hooks and JSON rendering (degrades with a warning without it).

Migration from 0.1: the installer moves a tailored `.agents/bin/verify` into `.agents/checks/turn.sh` and `full.sh`. Review both (they now receive changed files as arguments), then re-run harness-tailor to split out an edit tier.
